# Codex 工程工作流设计

## 目标

创建一套面向 OpenAI Codex 的高自主工程工作流。它吸收 Superpowers 中证据驱动、系统化调试、风险匹配验证和安全 Git 操作等有效原则，但不继承所有任务强制设计、强制 TDD、强制 worktree 或强制多 Agent 的刚性流程。

仓库内容默认使用中文，仅在表达更准确或属于固定名称时保留 Codex、Skill、Git、TDD、API、YAML 等必要术语。

## 交付形态

采用“全局核心 Skill + 可选项目级 AGENTS.md 模板”的组合：

```text
codex-engineering-workflow/
├── README.md
├── LICENSE
├── skills/
│   └── codex-engineering-workflow/
│       ├── SKILL.md
│       └── agents/
│           └── openai.yaml
├── templates/
│   └── AGENTS.md
├── tests/
│   └── scenarios.md
└── docs/
    └── superpowers/specs/
        └── 2026-07-15-codex-engineering-workflow-design.md
```

- `SKILL.md`：定义任务分级、执行流程、暂停条件、验证和交付规则。
- `agents/openai.yaml`：提供 Codex UI 使用的中文名称、简介与默认提示。
- `templates/AGENTS.md`：提供可复制到项目根目录的稳定安全边界，不重复完整工作流。
- `tests/scenarios.md`：记录压力场景、预期行为、基线结果和启用 Skill 后的结果。
- `README.md`：用中文说明定位、安装、使用方式、适用边界和与 Superpowers 的区别。

## 任务分级

Skill 先判断任务风险，再选择最轻但足够可靠的工作强度。

| 等级 | 典型场景 | 默认行为 |
|---|---|---|
| L0 只读 | 解释、查询、代码审查、状态汇报 | 只读检查并提供证据，不修改文件 |
| L1 轻量 | 文案、小配置、局部低风险修改 | 检查上下文后直接修改，执行最小相关验证 |
| L2 标准 | Bug、功能、重构、依赖调整 | 定位真源、形成简短内部计划、实现、针对性测试、检查 diff |
| L3 高风险 | 权限、迁移、生产部署、公共 API、并发、安全、破坏性操作 | 扩大审计和验证；遇到不可逆决定或缺少必要授权时暂停确认 |

等级可以在执行中调整。发现影响面、安全性或不可逆性高于预期时升级；确认变更完全局部且可逆时可降低不必要的流程负担。

## 核心流程

```text
读取用户目标
→ 检查仓库、项目规则与未提交改动
→ 判断 L0–L3 风险等级
→ 找到当前真源和最小修改边界
→ 实施或保持只读
→ 执行与风险匹配的验证
→ 检查 diff、Git 边界与剩余风险
→ 汇报结果
```

### 自主执行

- 能从代码、文档、Git、日志和工具中查到的信息，不询问用户。
- 小任务不强制编写设计文档或实施计划。
- Bug 修复先复现问题或建立可信证据，再修改。
- 有现成测试体系时优先补回归测试；没有测试基础设施时使用针对性构建、静态检查或真实运行验证。
- 连续两次出现同类失败时停止微调，重新检查错误原文、前置假设和替代方案。
- 多 Agent 仅用于互不干扰、能够明显节省时间的独立工作域。

### 暂停条件

仅在继续执行需要新增授权或关键业务判断时暂停，包括：

- 凭据、账号、密钥或只有用户掌握的业务意图；
- 不可逆删除、数据迁移或大范围覆盖；
- 生产环境变更、产生费用或影响真实用户；
- 对外发布、发送消息、创建 PR 或超出已授权范围的推送；
- 会显著改变结果的产品、架构或兼容性取舍。

普通实现细节、可通过仓库事实确定的选择以及安全可逆的局部修改不作为暂停理由。

## Git 与范围边界

- 开始修改前确认 Git 根目录、当前分支和 `git status --short`。
- 保留用户已有修改，不回滚、不覆盖、不混入当前任务。
- 不使用 `git reset --hard`、强制推送等破坏性命令，除非用户明确要求并确认风险。
- 不使用无差别 `git add .`；只暂存当前任务涉及的路径。
- 不借当前任务顺手扩大重构范围。
- 用户明确要求保存到 Git 仓库时，可以创建提交并推送；推送前检查 staged diff、提交范围和远端分支状态。

## 验证与交付

验证强度必须匹配风险：

- L1：执行最小相关检查，例如格式、单文件测试或可直接观察的结果。
- L2：执行针对性测试，并在合理成本内运行受影响模块的构建、静态检查或回归测试。
- L3：覆盖失败路径、数据与权限边界、回滚条件、生产前门禁和必要的端到端验证。

只有实际运行验证后才能声称“完成”“修复”或“通过”。如果环境限制导致关键验证无法执行，必须说明未验证内容、影响和替代证据。

交付汇报优先包含：

1. 已实现或已确认的结果；
2. 实际执行的验证及结果；
3. 必要的剩余风险或用户下一步。

## 与 Superpowers 的差异

本项目受 Superpowers 工程方法论启发，但进行独立重写，并针对 Codex 高自主执行方式调整。默认移除以下刚性要求：

- 所有任务强制 brainstorming；
- 所有代码变更强制 TDD；
- 强制创建 Git worktree；
- 强制多轮设计审批；
- 每个任务强制调用子 Agent；
- 为遵守测试顺序而删除已有实现；
- 简单修改也必须产生长计划文档。

保留的重点是：先看当前事实、保护用户修改、定位根因、控制范围、用证据验收，并在高风险边界前取得必要授权。

## 验证方案

### 格式验证

使用 Codex `skill-creator` 附带的 `quick_validate.py` 检查 Skill 名称、YAML frontmatter 和目录结构，并核对 `agents/openai.yaml` 与 `SKILL.md` 一致。

### 行为压力测试

至少验证以下场景：

1. 简单修改不会触发长设计、强制 TDD 或不必要提问；
2. Bug 修复会先找证据并执行回归验证；
3. 仓库存在用户未提交改动时不会覆盖或回滚；
4. 生产发布、不可逆删除或缺少授权时会暂停确认；
5. 连续失败时会改变假设和方法，而不是重复微调。

先记录未启用 Skill 的基线行为，再使用同类场景验证 Skill 能否修正真实缺陷。测试过程不接触生产环境，也不执行破坏性操作。

### 仓库检查

- 不保留 TODO、TBD、未替换占位符或无效路径；
- 检查 Markdown、YAML、安装命令和最终 diff；
- README、Skill 正文、模板和测试说明以中文为主；
- 提交前核对暂存文件，推送后核对远端 `main` 状态。

## 非目标

- 不复制或重新发布 Superpowers 的完整 Skill 集；
- 不引入自动联网反馈、遥测、排行榜或无限循环；
- 不创建常驻后台进程或 hooks；
- 不替代项目自身的架构、测试、安全和发布规范；
- 不保证单一工作流适合所有技术栈，项目规则始终优先。
